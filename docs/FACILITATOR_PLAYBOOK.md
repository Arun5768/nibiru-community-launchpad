# Nibiru first-build lab: facilitator playbook

## Outcome

Every participant should leave with at least one verifiable public artifact: a Testnet 2 address, a confirmed transaction, or a repository containing their build notes. The event is measured by completed actions, not registrations.

## Audience and room

- 25–60 selected developers, students, founders, and technical creators.
- One facilitator, one technical lead, and one mentor per 12–15 participants.
- Participants work in pairs when possible so nobody is blocked alone.
- Test the venue internet and Nibiru RPC from the room before doors open.

## 90-minute run of show

| Time  | Activity                                            | Exit check                                  |
| ----- | --------------------------------------------------- | ------------------------------------------- |
| 00–10 | Why Nibiru, safety, and the single workshop outcome | Everyone understands testnet-only rules     |
| 10–25 | Add Nibiru Testnet 2 and inspect the live network   | Correct chain ID: 6911                      |
| 25–40 | Fund a test account and complete one guided action  | Public transaction hash captured            |
| 40–70 | Pair build sprint with mentor checkpoints           | A working interaction or documented blocker |
| 70–85 | Verify transactions and demo selected results       | Evidence receipt or public repository       |
| 85–90 | Contributor next step and 7-day challenge           | Follow-up owner and deadline recorded       |

## Safety script

“We use Testnet 2 only. Never paste a seed phrase or private key into this site, a form, a chat, or a shared computer. Testnet tokens have no monetary value. We verify only public addresses and transaction hashes.”

## Metrics

- Registration → attendance conversion.
- Correct wallet/network setup rate.
- Number of verified public transactions.
- Number of public build repositories or evidence receipts.
- Blockers grouped by documentation, tooling, network, or concept.
- Seven-day and 30-day builder follow-up.

## Follow-up loop

Within 48 hours, send resources and the next small challenge. Within seven days, collect public build links. Within 30 days, publish an anonymized retrospective with what worked, what failed, and which documentation improvements should be proposed upstream.
