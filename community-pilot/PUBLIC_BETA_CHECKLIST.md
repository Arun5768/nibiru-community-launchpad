# Independent public-beta checklist

Use this checklist to move Nibiru Debug Desk from a working utility to an
evidence-backed community case study. This remains an independent experiment;
do not imply Nibiru sponsorship, partnership, approval, or endorsement.

## 1. Private rehearsal

- Run the network, address, transaction, issue-guide, and report flows.
- Test the session plan with two helpers before inviting participants.
- Confirm every link against the current official Nibiru documentation.
- Prepare a fallback explanation if the public testnet or faucet is unavailable.
- Never collect a seed phrase, private key, or participant wallet export.

Exit condition: the facilitator can reproduce the complete flow without
improvising a network value or safety instruction.

## 2. Small public beta

- Invite 5–10 builders rather than optimizing for registration count.
- Mark the event and materials as independently organized.
- Ask each participant to choose one verifiable outcome: correct network,
  confirmed public transaction, public repository, or documented blocker.
- Use aggregate counts only in the Pilot Evidence tracker.
- Request permission before publishing identifiable photos, quotes, or handles.

Exit condition: at least one participant completes an action, or the group
produces a reproducible blocker that is useful to maintainers.

## 3. Evidence review

- Remove duplicates and test entries from the counts.
- Check that completions and follow-ups do not exceed attendance.
- Open every public evidence link in a signed-out browser.
- Separate observed facts from facilitator interpretation.
- Keep the report status as `planned` until the session has happened.

Exit condition: another person can trace every public claim to evidence or a
clearly stated counting rule.

## 4. Publish the case study

- Export the Markdown retrospective from the live app.
- Add the date, format, aggregate results, recurring blockers, and next change.
- Link only public repositories, transactions, and consented media.
- State limitations, including small sample size and unavailable follow-up data.
- Add the report to this repository in a dated `community-pilot/results/` file.

Exit condition: the report is useful even if the outcome was smaller than
expected. Honest negative results are still evidence.

## 5. Responsible follow-up

- Share one concise update through the appropriate public community channel.
- Link the utility, case study, and any reproducible technical issue.
- Ask for feedback on a specific finding, not approval based on event photos.
- Avoid repeated direct messages and do not promise funding or official status.

Exit condition: feedback is captured as a concrete improvement, documentation
change, or well-scoped upstream contribution.
